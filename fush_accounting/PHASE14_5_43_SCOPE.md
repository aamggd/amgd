# Phase 14.5.43 — Accounting Idempotency & Duplicate-Posting Protection

## الهدف
منع إنشاء قيود محاسبية مكررة عند إعادة المحاولة أو الضغط المزدوج أو إعادة تنفيذ نفس الحدث الآلي، من دون منع الحالات المشروعة التي يمكن أن تنتج أكثر من قيد لنفس المصدر.

## النطاق المنفذ
- إضافة `postingKey` اختياري وفريد إلى `journal_entries`.
- إضافة `PostingKey.of(sourceType, sourceId, discriminator?)` لتوليد مفتاح حدث ثابت.
- إضافة `insertEntryOnce` / `postEntryOnce` بحيث تعيد نفس القيد عند تكرار نفس الحدث بدل إدخال قيد جديد.
- رفض إعادة استخدام نفس `postingKey` إذا اختلف تاريخ القيد أو العملة أو سعر الصرف أو الحسابات أو المدين/الدائن أو البيان (`POSTING_KEY_PAYLOAD_MISMATCH`).
- حماية أحداث مستقرة مثل المبيعات، التحصيلات، المرتجعات، المشتريات، دفعات الموردين، الجرد، حركات الإنتاج الأساسية، الإهلاك، فروق العملة والعكس.
- إبقاء القيود اليدوية والتصحيحات المتكررة المشروعة وإعادة إقفال السنة بلا مفتاح عام قسري.
- Migration فرعي `34 -> 35` يضيف العمود والفهرس الفريد دون حذف بيانات تاريخية.
- Backfill تاريخي للمصادر المستقرة فقط عندما يكون زوج `sourceType/sourceId` فريدًا. التكرارات التاريخية القديمة تبقى `postingKey = NULL` للمراجعة بدل حذفها أو إخفائها.
- Trigger يمنع تغيير `sourceType/sourceId/postingKey` بعد أن يصبح القيد `POSTED`.

## ملاحظات الدمج
- Schema `35` هو **BRANCH ONLY / PROVISIONAL** ويجب على المحادثة الرئيسية إعادة ترقيمه إذا حجز فرع آخر الرقم نفسه.
- لا يوجد destructive migration.
- `Application ID` والإصدار التجريبي للفرع لم يتغيرا.
- التوقيع الرسمي غير منفذ داخل CI.
